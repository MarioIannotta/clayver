# Contributing to Clayver

Thanks for helping. Clayver is in-app customer support that runs entirely in
the developer's own Firebase project: native SDKs, a Flutter plugin, a
dashboard, a setup CLI and a Firebase backend, all in this repository and all
released together under one version.

By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).
Report security issues privately, as described in [SECURITY.md](SECURITY.md),
not in public issues.

## Repository layout

| --- | --- | --- |

| `ios/` | iOS SDK `ClayverSDK` (Swift, SwiftUI). `Package.swift` at the repository root publishes it (Swift Package Manager only). | Xcode 16, iOS 15+ |

| `flutter/` | Flutter plugin `clayver`, a thin Pigeon bridge over the native SDKs. | Flutter stable (3.32+) |
| `dashboard/` | Self-hostable agent dashboard (React + Vite). | Node 20+ |
| `packages/core` | `@clayver/core`: typed data model and Firebase data-access layer used by the dashboard. | Node 20+ |

| `examples/` | Example apps for iOS, Android and Flutter. | |
| `docs/` | Architecture, security model, identity verification, push, testing, the [production checklist](docs/production-checklist.md) and [releasing](docs/releasing.md). | |
| `scripts/` | Release tooling: `version.mjs`, `check-versions.mjs`, `changelog-section.mjs`. | Node 20+, no dependencies |

## The contract-first rule

Every platform implements the same contract, so changes start there:

1. **Change the contract first.** A new or changed database path, field,
   rule, callable or push payload goes into
   [`firebase/database.schema.md`](firebase/database.schema.md). A new or changed
   public SDK API goes into [`docs/sdk-api.md`](docs/sdk-api.md), with its
   Swift, Kotlin and Dart signatures.
2. **Then the backend**: rules (edit `firebase/scripts/build-database-rules.mjs`,
   then `pnpm --filter @clayver/functions rules:build`), functions and emulator
   tests.
3. **Then every client**: iOS, Android, Flutter, `@clayver/core` and the
   dashboard, and the CLI if it writes or reads the data.

A pull request that changes behaviour on one platform without the contract, or
leaves a platform behind without saying so, will be asked to fix that first.
Keep iOS and Android at parity; Flutter forwards to them.

## Setting up

```sh
corepack enable            # pnpm version comes from package.json "packageManager"
pnpm install
pnpm build                 # turbo run build: core, functions, dashboard, CLI
```

The emulator suite also needs Java 11+ (the Firebase CLI comes from the
workspace's devDependencies).

## Commands

All TypeScript packages are driven by [Turborepo](https://turbo.build) from the
repository root:

| Command | Does |
| --- | --- |
| `pnpm build` | Builds every package (`turbo run build`). |
| `pnpm test` | Runs every package's tests (`turbo run test`). This includes the emulator suite, so it needs Java. For unit tests only: `pnpm turbo run test --filter='!@clayver/firebase-tests'`. |
| `pnpm typecheck`, `pnpm lint` | Type-checks and lints every package. |
| `pnpm test:emulators` | Builds the functions and runs the rules, storage and functions tests against the Firebase Emulator Suite (project `demo-clayver`). |
| `pnpm emulators` | Starts the same emulators with the rules and functions loaded and keeps them running, for manual testing with the dashboard (`pnpm --filter @clayver/dashboard dev:emulators`) or the example apps. |
| `pnpm --filter <package> <script>` | One package, e.g. `pnpm --filter clayver test` or `pnpm --filter @clayver/dashboard dev`. |
| `node scripts/check-versions.mjs` | Checks that every package carries the same version. |

### Platform tests

The native SDKs and the Flutter plugin are not part of the pnpm workspace; run
their tests with their own tools (CI runs all of them, see
`.github/workflows/ci.yml`):

```sh
cd android && ./gradlew :clayver:testDebugUnitTest     # JDK 17 and an Android SDK
cd flutter && flutter pub get && flutter analyze && flutter test
# iOS, on macOS, from the repository root:
xcodebuild test -scheme ClayverSDK -destination 'platform=iOS Simulator,name=iPhone 16' -skipPackagePluginValidation
```

FCM cannot be emulated. Under the Functions emulator, pushes are written to
`clayverEmulator/pushes` instead; see [docs/testing.md](docs/testing.md).

## Pull requests

- Branch from `main` and keep each pull request to one change.
- Add or update tests: emulator tests for rules and functions, unit tests for
  the SDKs, CLI and dashboard data layer.
- Run `pnpm turbo run build typecheck lint` and the tests for every part you touched.
- Add a line to the `## [Unreleased]` section of [CHANGELOG.md](CHANGELOG.md)
  for anything a user of Clayver would notice (Added, Changed, Deprecated,
  Removed, Fixed, Security).
- Never commit secrets, `google-services.json`/`GoogleService-Info.plist` of a
  real project, or `.env` files with real values.
- Do not edit version numbers by hand; releases set them (below).

## Releasing

Maintainers only. Every package in the repository shares one version, set by
`scripts/version.mjs`:

1. Make sure `main` is green and the `## [Unreleased]` section of
   `CHANGELOG.md` lists everything in the release.
2. Run the version script with the new [semantic version](https://semver.org):

   ```sh
   node scripts/version.mjs 0.2.0 --dry-run   # shows every file it would change
   node scripts/version.mjs 0.2.0
   ```

   It updates every `package.json`, `flutter/pubspec.yaml`,
   `Clayver.sdkVersion` (Swift), the Android `version`, the version constants
   in `@clayver/core` and the CLI, the install snippets in the READMEs, and
   moves the Unreleased changelog entries under `## [0.2.0] - <today>`.
   `node scripts/check-versions.mjs` then passes.
3. Commit, tag and push:

   ```sh
   git commit -am "Release v0.2.0"
   git tag v0.2.0
   git push origin main v0.2.0
   ```

4. The `v*` tag starts `.github/workflows/release.yml`: it checks that the tag
   matches every version source, then publishes the Android SDK to Maven
   Central, the Flutter plugin to pub.dev, and `clayver`
   to npm, and creates the GitHub Release with the changelog section. Swift
   Package Manager resolves the tag directly. A registry without credentials
   is skipped with a notice.

Versions with a pre-release suffix (`0.3.0-beta.1`) are published as
pre-releases (npm dist-tag `next`, GitHub pre-release). One-time registry
setup and the list of secrets are in [docs/releasing.md](docs/releasing.md).
