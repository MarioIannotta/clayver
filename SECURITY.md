# Security policy

Clayver runs in each developer's own Firebase project, so a flaw in its
security rules, Cloud Functions or SDKs can expose the support conversations of
every app that uses it. Thank you for reporting issues responsibly.

## Supported versions

All Clayver packages share one version number. Security fixes are released for:

| Version | Supported |
| --- | --- |
| Latest minor release (currently 0.1.x) | Yes |
| Older minor releases | No: upgrade with `npx clayver@latest update` and the latest SDKs |

Before 1.0, only the latest minor release receives fixes. Fixes to the rules
and functions reach a project when its developer runs `npx clayver update`;
SDK fixes need an app update.

## Reporting a vulnerability

**Do not open a public issue, pull request or discussion.**

Report it privately through GitHub: open the repository's **Security** tab and
choose **Report a vulnerability** (GitHub private vulnerability reporting /
security advisories). Include:

- the affected component and version (rules, a function, an SDK, the CLI, the dashboard);
- steps to reproduce, ideally against the Firebase Emulator Suite
  (`pnpm emulators`) rather than a real project;
- the impact you see (for example "customer A can read customer B's messages").

What to expect:

- an acknowledgement within 3 working days;
- an assessment and, if confirmed, a fix plan within 10 working days;
- a coordinated release: we publish the fix, then a GitHub security advisory
  (with a CVE when appropriate) crediting you unless you prefer otherwise.

Please do not test against Firebase projects you do not own, and do not access,
modify or keep other people's data.

## Scope

In scope:

- **Security rules**: `firebase/database.rules.json` (generated by
  `firebase/scripts/build-database-rules.mjs`) and `firebase/storage.rules`.
  For example a customer reading another customer's data, writing
  server-maintained fields, spoofing `senderType`/`senderId`, escaping a block,
  or crossing workspace boundaries.
- **Cloud Functions** (`firebase/functions`): role management
  (`clayverBootstrapAdmin`, `clayverSetAgentRole`), data
  export and deletion, rate limiting, push fan-out (sending to the wrong device
  or leaking content).
- **SDK authentication handling** in the iOS, Android and Flutter SDKs,
  `@clayver/core` and the dashboard: following the host's Firebase Auth user,
  logout, custom claim refresh, agent mode role detection, push token registration and
  migration between users, storing anything sensitive on the device.
- **The `clayver` CLI**: files it writes into an app, role grants, and the
  commands it runs.

Out of scope:

- Misconfiguration of a developer's own project that the
  [production checklist](docs/production-checklist.md) warns against (for
  example granting agent roles to accounts you don't control, or leaving App
  Check off).
- Vulnerabilities in Firebase, Google Cloud or third-party dependencies
  themselves (report those upstream; tell us if Clayver needs to react).
- Denial of service through Firebase quotas and billing; see the rate limit
  and budget sections of the production checklist.

The security model is described in [docs/security.md](docs/security.md).
